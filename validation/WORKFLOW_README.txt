WorkCert 0.2 — worked public-data examples

Run from the project root after installing the software and validation dependencies:
  python validation/user_workflow.py --case pla
  python validation/user_workflow.py --case cyclic
  python validation/user_workflow.py --case all

Inputs are included. The cyclic example verifies the original XLSX against the
Zenodo MD5; if the source is absent, the script downloads that fixed record.
All result values, table files and query comparisons are regenerated by the script.

1. Compression-database exchange and variable-stroke screening

The input is the 46 archived PLA+ compression responses and the matching numeric
specimen masses in Mass_and_Crash_Indicators.xlsx, Mendeley Data version 4,
DOI 10.17632/v7p6y654ft.4. The example demonstrates an administrator/consumer
workflow using these public experimental records.

An archive administrator constructs a response table with an absolute 1 J bound
on arbitrary-window work, a 129-point cap, an explicitly selected work-priority
method, absolute-peak retention, and the recorded mm/kN units. The table is saved
and reloaded. The consumer queries 10, 20, 30 and 40 mm, plus 10--20, 20--30 and
30--40 mm intervals. All these requests lie within all 46 recorded loading domains
and within the maximum strokes reported in the source indicator workbook.

For travel u, mass m in kg, force in kN and displacement in mm:
  EA(u)  = integral_0^u F(x) dx                    [J]
  SEA(u) = EA(u) / m / 1000                       [kJ/kg]
  MCF(u) = EA(u) / u                             [kN]
  PCF(u) = max_{0<=x<=u} F(x)                     [kN]
  CFE(u) = MCF(u) / PCF(u)                       [dimensionless]
The peak is defined over the queried prefix. A small triangle fixture independently
checks these conversions before processing the experimental records.

If e is the stored maximum prefix-work error and delta the force error, then:
  EA lies in EA_hat +/- e;
  SEA and MCF intervals follow by division by the positive source mass and u;
  PCF lies in PCF_hat +/- delta;
  CFE lies between (EA_hat-e)/(u*(PCF_hat+delta)) and
                  (EA_hat+e)/(u*(PCF_hat-delta)) when the latter denominator is positive.
All 184 finite CFE intervals and all 138 interval-work requests are checked against
the full piecewise-linear references. Masses are the fixed values in the archive;
the intervals describe reconstruction, not mass or experimental uncertainty.

The workflow compares all 1,035 design pairs at each of four travel limits.
Nonoverlapping SEA intervals resolve an ordering. Responses incident to any
overlapping comparison are refined at 0.25 J and then 0.0625 J, retaining the
same point cap. An unmet tolerance is kept as an explicit output. If comparisons
still overlap, the administrator returns exact source-reference EA scalars for
only the requested curve/travel pairs. These are separately labelled scalar
responses, not additional compressed force curves.

Outputs under workflow_results/pla_exchange/:
  summary.json: retained budgets, resolved comparisons and scalar follow-up;
  queries_stage_*.csv: EA, SEA, MCF, PCF, CFE, exact references and error intervals;
  windows_stage_*.csv: interval-work queries and their bounds;
  pairs_stage_*.csv: every ordering decision, including unresolved comparisons;
  query_specific_scalar_responses.json and pairs_after_scalar_followup.csv;
  mass_and_metric_source_audit.csv: source mass and indicator-window audit;
  tables/: every exchanged WorkCert table, with hashes in summary.json.

An independent consumer needs only a received table and its specimen mass:
  python examples/query_exchange.py validation/workflow_results/pla_exchange/tables/stage_0/STWC-1.json --mass-g 16.2 --strokes 10 20 30 40
The consumer reads no dense CSV or source workbook. It returns the engineering
metrics and their reconstruction intervals in JSON. verify_workflow.py compares
this client with the producer outputs and audits every saved workflow table.

The source indicator workbook reports EA at its delta_max, not necessarily the
end of the archived force curve. The audit evaluates that same travel. Small
endpoint differences are retained, rather than using the published EA as an
independent truth or silently replacing the supplied force history.

2. Full chronological cyclic-bending path

The input is the complete S1-L1 record in Zenodo 10.5281/zenodo.10829958:
125,157 displacement/force pairs in mm/kN from cyclic bending of a stainless
steel rectangular hollow section. See data/extended/DATA_ATTRIBUTION.txt.

The script partitions at every exact displacement reversal and repeated-coordinate
pair. Every original chronological interval is represented exactly once. A turning
point belongs to adjacent branches. Equal-displacement force changes remain explicit
zero-work events. No smoothing, jitter threshold, contact alignment, or first-passage
selection is applied. A descending branch is stored in ascending query coordinates
with its chronological start/end and direction retained. Its physical directed
work is response.work(end_x) - response.work(start_x).

The total requested work-error budget is 0.001 times the sum of absolute directed
branch work. It is allocated in proportion to those absolute branch integrals.
Each branch has a 129-point cap and window-error stopping. The sum of the actual
branch-window bounds is checked against the maximum chronological cumulative
error. The latter is computed independently at every reference node and every
interior residual zero. Cap failures are reported explicitly.

This signed F dx is a path integral. The record is not assumed closed, so the
reported total is not labelled dissipated loop energy or crashworthiness EA.

Outputs under workflow_results/cyclic_path/:
  summary.json and branch_metrics.csv: complete accounting and branch error metadata;
  tables/: every branch table with file hashes in branch_metrics.csv;
  chronological_path.npz: full path, reconstructed force and cumulative work error;
  longest_branch_reference.csv and longest_branch_reduced.csv: a reproducible
  illustrative long branch selected solely by its reference-node count.

protocol.json documents the deterministic workflow settings. summary_all.json records
the software version and core-source SHA-256 used to compute the examples.
Run the independent saved-output audit with:
  python validation/verify_workflow.py
